# Restaurant Reservation

Платформа бронирования для ресторанов, коворкингов и спортивных заведений. Гости бронируют время на столик, рабочее место или корт, владельцы управляют заведениями и расписанием и видят весь день целиком. Небольшой ML-сервис оценивает вероятность неявки для каждой брони, на основе этого требуется депозит и допускается контролируемый овербукинг.

## Возможности

- JWT-аутентификация, роли `CUSTOMER`, `VENUE_OWNER` и `ADMIN`
- Заведения, ресурсы и недельное расписание с учётом часовых поясов
- Генерация слотов с кэшем в Redis, который сбрасывается после коммита
- Защита от двойного бронирования через exclusion constraint в PostgreSQL, оптимистичные и пессимистичные блокировки
- Идемпотентное создание брони через заголовок `Idempotency-Key`
- Депозит через порт платёжного шлюза, для разработки используется фейковый шлюз
- Прогноз неявки (CatBoost) с запасным поведением, если ML-сервис недоступен
- Резервные брони: слот с единственной рискованной неоплаченной бронью можно перебронировать
- Фоновые задачи: истечение неоплаченных броней и напоминания, под защитой ShedLock
- История брони: каждое изменение статуса и каждый шаг платежа записываются вместе с исполнителем
- Дневной список всех броней заведения для владельцев и админов
- Health-эндпоинт, Swagger UI, ошибки в формате RFC 7807

## Стек

Java 21, Spring Boot 3.3, Spring Security, Spring Data JPA, Flyway, PostgreSQL 16, Redis 7, springdoc, Testcontainers.
ML-сервис: Python, Flask, CatBoost.

## Архитектура

Clean Architecture, зависимости направлены внутрь:

```
presentation    контроллеры, запросы, ответы, обработка ошибок
application     use case, DTO, порты, политики
domain          модели, порты репозиториев, доменные сервисы и исключения
infrastructure  JPA-адаптеры, безопасность, кэш, платежи, ML-клиент, планировщики
```

ML-сервис лежит в `ml-service/` и деплоится отдельно.

## Запуск в Docker

```
docker compose up --build
```

Поднимаются PostgreSQL, Redis, ML-сервис и бэкенд. Модель обучается на синтетических данных при сборке образа.

| Сервис | Порт по умолчанию | Переопределение |
| --- | --- | --- |
| Бэкенд | 8080 | `BACKEND_PORT` |
| PostgreSQL | 5432 | `POSTGRES_PORT` |
| Redis | 6379 | `REDIS_PORT` |
| ML-сервис | 5002 | `ML_PORT` |
| Сайт | 3100 | `FRONTEND_PORT` |

Пример, если порт 8080 занят:

```
BACKEND_PORT=8081 docker compose up --build
```

Сайт откроется на `http://localhost:3100`. Для проверки API откройте `http://localhost:8080/swagger-ui.html`, выполните `POST /api/auth/login` и нажмите Authorize с полученным токеном.

Compose включает dev-данные, поэтому доступны пользователи (пароль `password123`):

| Email | Роль |
| --- | --- |
| owner@dev.local | VENUE_OWNER |
| alice@dev.local | CUSTOMER |
| bob@dev.local | CUSTOMER |
| admin@dev.local | ADMIN |

Вне локальной разработки задайте свой `JWT_SECRET`.

## Сайт

Next.js (App Router), каталог `frontend/`. Структура: `src/modules/<модуль>/<модуль>.jsx` и `<модуль>.css`, общие компоненты, api и хуки в `src/shared`. Модули: auth, venues, booking, my-bookings, owner-dashboard. Запросы к `/api` проксируются на бэкенд через rewrites, адрес задаётся `BACKEND_URL` при сборке.

Локально:

```
cd frontend
npm install
BACKEND_URL=http://localhost:8080 npm run dev
```

Сайт будет на `http://localhost:3100`.

## Локальный запуск

Нужны JDK 21, Maven и запущенные PostgreSQL и Redis (например, `docker compose up postgres redis`).

```
mvn spring-boot:run
```

Основные настройки лежат в `src/main/resources/application.yml` и переопределяются переменными окружения: `DB_URL`, `REDIS_HOST`, `ML_BASE_URL`, `JWT_SECRET`.

## Тесты

```
mvn test
```

Интеграционные тесты запускают PostgreSQL и Redis через Testcontainers, поэтому Docker должен быть запущен. Тесты ML-сервиса:

```
cd ml-service
pip install -r requirements-dev.txt
pytest
```

## История брони

Каждое изменение статуса, постановка в резерв, напоминание и шаг платежа сохраняются в `booking_events` с JSON-данными. Первое поле данных это исполнитель: пользователь с id и ролью либо `system` для фоновых задач. События пишут адаптеры репозиториев, поэтому записывается любой путь, который меняет бронь.

## Прогноз неявки

При создании брони бэкенд отправляет её признаки в ML-сервис. Если вероятность выше 0.4, требуется депозит. Если единственная неоплаченная бронь слота имеет вероятность 0.5 и выше, вторая бронь принимается как резервная и занимает слот, когда первая истекает или отменяется. Если ML-сервис медленный или недоступен, запрос обрабатывается без прогноза, а сам сервис пропускается на 30 секунд.
